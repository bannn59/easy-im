# 项目功能地图调研

## Goal

摸清 **easy-im 现有、用户可感知的功能**，产出可导航的功能地图。  
**不写产品代码**；成果写入本任务 `research/`，供后续规划与新人上手使用。

## Background

- 仓库为 monorepo 目标形态（Go 后端 + React/TS 前端），见 `.trellis/spec/`。
- 截至任务创建时，应用源码（`backend/`、`frontend/`、路由、API、页面）可能仍为空或极少；调研必须 **如实记录证据**，禁止把 bootstrap 假设当成已实现功能。
- 「功能」指用户或运营能感知的能力（登录、会话列表、发消息等），不是按文件名罗列。

## Scope

### In scope

1. 从 **路由、菜单、页面、API/协议、模块目录、配置、测试** 反推功能清单。
2. 按用户可感知能力 **分组**（例如：账号与登录、会话与消息、在线状态、设置……）。
3. 每个功能条目包含：
   - 功能名
   - 入口（页面 / 路由 / 命令 / 深链）
   - 关键代码位置
   - 依赖的服务 / 表 / 配置
   - 相关测试（若有）
4. `research/` 下可导航 `index` + 分组明细。
5. 标注 **高风险/高耦合** 与 **适合新人下手** 的模块（有证据才标；无代码时明确「尚无模块可评」）。

### Out of scope

- 实现新功能或脚手架产品代码。
- 重写 `.trellis/spec/`（除非调研发现与事实严重冲突，仅记入 research 建议，不在本任务改 spec）。
- 把 Trellis 工作流/agent 工具当成 IM 产品功能（可在「仓库元能力」附录中一笔带过，不进主功能地图）。

## Constraints

- 每条功能声明必须有 **证据**（文件路径、符号、路由字符串、测试名）；无证据标 `status: not_found` / `planned_only`。
- 语言：research 文档可用中文；路径、标识符保持原文。
- 不修改 `backend/` / `frontend/` 产品源码（当前亦可能不存在）。

## Acceptance Criteria

- [x] 存在 `research/index.md` 作为可导航总览（分组链接 + 统计：已实现 / 部分 / 未找到）。
- [x] 每个用户可感知功能分组有独立明细文件，或在 index 中完整列出且字段齐全。
- [x] 每条功能含：功能名、入口、关键代码、依赖、测试、证据状态。
- [x] 有「高风险/高耦合」与「适合新人下手」专节；无代码时明确说明无法评估的原因。
- [x] 有「调研方法与覆盖范围」说明：扫了哪些入口、哪些目录不存在。
- [x] 未把 `.trellis/spec` 中的 bootstrap 假设写成「已上线功能」。
- [x] 本任务不产生产品代码改动。

## Notes

- 若调研结论为 **零产品功能**，仍视为成功交付：空地图 + 方法记录 + 建议下一步脚手架，满足 AC。
- 复杂任务：需 `design.md`（调研方法/产出结构）与 `implement.md`（执行清单）后，再 `task.py start`。
