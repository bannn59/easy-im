# 群聊：建群 + 收发消息 + 成员面板

**任务**: `08-01-group-chat`  
**日期**: 2026-08-01  
**类型**: 复杂任务 — 后端 API + 前端 UI

## 1. 背景与问题

easy-im 当前只有 **1:1 会话**：
- `ConversationService.OpenDirect` 建双人会话（需互为好友）。
- DB 表 `conversations`（含 `title`/`created_by`）+ `conversation_members` 已支持多成员，但**没有服务层创建群的方法**。
- **前端已预留群聊 UI**：`ConversationRoom.tsx` 有 `isGroup = members.length > 2` 判断、群标题显示、群已读取 min；`AppShell.tsx` 有 `conversationListTitle` 群标题逻辑——但**没有创建群入口和后端 API**。

**结论**: 基础设施已就绪，缺「创建群」这一垂直切片（后端 API + 前端入口 + 成员面板）。

## 2. 目标

实现群聊最小闭环：
1. **后端**：`POST /v1/conversations/groups` 创建群（选好友成员 + 群名），实时广播新群会话。
2. **消息收发**：群内成员发消息/收消息/历史——复用现有 `POST /messages` + WS 广播（成员列表驱动）。
3. **前端**：创建群对话框（选好友 + 群名）、会话列表区分群/单聊、成员面板（查看成员）。

### 成功标准（验收）

1. **建群 API**：`POST /v1/conversations/groups`（body: `{title, member_ids}`）创建群，成员 ≥ 2（含创建者），创建者为群主（`created_by`）。
2. **权限**：只有好友能入群（成员必须在创建者的好友列表）；非成员不能访问群会话（现有 ACL 复用）。
3. **消息收发**：群内成员发消息，WS 实时推给**群内所有在线成员**（跨节点 fanout 复用）。
4. **前端创建群**：对话框选好友（可多选）+ 输群名，提交后跳转群会话。
5. **会话列表**：群会话显示群名（无群名时显示「未命名群」），单聊显示对方昵称——现有逻辑校验。
6. **成员面板**：群会话内显示成员列表（含头像/昵称占位），打开/关闭。
7. **实时性**：创建群后，被拉入成员刷新可见（列表出现新群）；不要求实时弹窗。
8. **测试全绿**：`go test ./...` + `npm run build` 通过。

### 非目标

- **不做** 成员管理（拉人/退群/踢人/转让群主）——后续任务。
- **不做** 群名修改、群头像。
- **不做** 群已读明细（按成员列出谁已读）。
- **不做** 音视频。

## 3. 约束与边界

- **复用现有表**：`conversations` + `conversation_members`，不加表。
- **复用现有消息链路**：`MessageService.Send` 的成员 ACL + `hub.BroadcastToConversation` 已按成员列表广播，群聊零改造。
- **复用现有 fanout**：跨节点群消息已由 `08-01-p7` 的 Kafka fanout 覆盖（按 `ListMemberIDs` 投递）。
- **好友校验**：成员必须是创建者好友（复用 `friends.AreFriends`）；创建者自己不必是"自己的好友"（特例）。
- **成员数**：≥2（含创建者）；上限可设（如 50）防滥用，由设计定。
- **群主**：`created_by` 即群主；本期无转让。

## 5. 验收测试

- `cd backend && go test ./...` 全绿。
- `cd frontend && npm run build` 全绿。
- 手动 E2E：两个用户互为好友 → 用户 A 创建群（含 B）→ 双方刷新会话列表见群 → A/B 发消息互相实时收到 → 群内成员面板显示两人。

## 6. 非目标明细（防范围膨胀）

- 不加 `conversation_type` 字段（用成员数 >2 判定群，现有前端已如此）。
- 不做群消息的「@所有人」、置顶、免打扰。
- 不做拉人实时通知（刷新可见即可）。
