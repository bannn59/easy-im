# wrk 并发压测与水平扩展基线

**任务**: `08-01-obs-loadtest-run`  
**日期**: 2026-08-01  
**类型**: 复杂任务（child）— 压测执行与报告

## 1. 背景与问题

需要量化 easy-im 的并发能力：单机吞吐是多少？水平扩展 2–3 节点（经负载均衡器）后吞吐提升多少？这是后续优化与容量规划的依据。

**依赖**: 本任务依赖 `08-01-obs-metrics` 的 `/metrics` 端点（压测中观察指标增长）。

## 2. 目标

用 `wrk` 压测 HTTP 接口（会话/好友/鉴权/消息），用轻量脚本单独测 WS 长连接，产出单机 vs 2 节点 vs 3 节点（经 LB）的对比报告。

### 成功标准（验收）

1. **压测脚本可复现**：存在 `scripts/loadtest.sh`（或 make target）+ 数据准备脚本（准备 N 用户/会话/消息）。
2. **接口覆盖**：wrk 覆盖会话列表、好友列表、鉴权（登录/注册）、HTTP 消息（发送/历史）。
3. **WS 单独测**：轻量脚本测 WS 连接数上限（wrk 不测 WS），结果单独报告。
4. **多节点对比**：单机 vs 2 节点 vs 3 节点（经 nginx/caddy LB），各跑同参数 wrk，记录 RPS + 延迟（p50/p99）+ 错误率。
5. **环境记录**：记录机器规格、Go 版本、Kafka/Postgres 部署方式、wrk 版本、参数（connections/threads/duration）。
6. **报告产出**：对比报告（表格 + 结论：扩展是否线性、瓶颈在哪），存于本任务 `research/`。
7. **metrics 佐证**：压测时抓取 `/metrics`，报告里附带关键指标增长（CPU/连接数/消息吞吐）。

### 非目标

- 不做生产环境压测（仅本机/开发环境）。
- 不做 WS 长连接消息吞吐压测（只测连接数上限）。
- 不产出调优结论之外的优化实现（发现问题另开任务）。

## 3. 约束与边界

- **wrk 版本**：官方 `wg/wrk`（github.com/wg/wrk）。
- **LB**：nginx 或 caddy，dev 单机；配置进版本库（`deploy/` 或 `scripts/`）。
- **数据准备**：需要预置用户、会话、好友、历史消息，保证压测接口有真实数据可读。
- **鉴权接口**：登录/注册含密码哈希，可能是瓶颈——需记录。
- **WS 压测**：轻量脚本（如 Go/Node 写的连接池压测），只测并发连接数上限，不测帧吞吐。
- **参数固定**：单机与多节点跑**完全相同的** wrk 参数（如 `-c 200 -t 8 -d 30s`），保证可比。

## 4. 交付物

1. `scripts/loadtest.sh`：wrk 压测主脚本（准备数据 → 跑单机 → 跑多节点 → 汇总）。
2. `scripts/prepare_data.go` 或 `.sh`：数据准备脚本。
3. LB 配置（nginx/caddy）进版本库。
4. WS 连接压测脚本。
5. 对比报告（表格 + 结论）于 `research/`。
6. 环境与复现说明（README 或报告头部）。

## 5. 验收测试

- `scripts/loadtest.sh` 可一键跑通（单机阶段）。
- 对比报告包含：单机 / 2 节点 / 3 节点 的 RPS、p50、p99、错误率，以及 metrics 抓取的关键值。
- 结论明确：水平扩展是否接近线性、主要瓶颈。

## 6. 非目标明细

- 不做跨机器部署（同一台机器多端口模拟多节点）。
- 不做前端压测。
