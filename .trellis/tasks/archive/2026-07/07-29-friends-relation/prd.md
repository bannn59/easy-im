# 好友关系 MVP（请求 / 同意 / 列表）

## Goal

提供最小可用的好友关系：用户按**对方注册邮箱**发起好友请求；**对方同意后**双方互为好友（可拒绝）；双方能看到好友列表与待处理请求。本任务 **不** 改造建会话入口（→ `07-29-friends-open-chat`）。

## Background

- 父任务：`07-29-friends-chat`。
- 代码现状：无好友表 / API / UI；`users.email` 唯一，无 username。

## Confirmed Facts

- `users.email` 唯一；无 username / 展示名搜索。
- 会话与消息链路已存在；本任务不改 `POST /v1/conversations`。

## Dependencies

- 无前置子任务。
- **后置**：`07-29-friends-open-chat` 依赖本任务可验收的「已是好友」关系与列表能力。

## Requirements

- R1. 登录用户可输入对方注册邮箱，向其发起好友请求（状态 pending）。
- R2. 被请求方能列出待处理请求，并 **同意** 或 **拒绝**。
- R3. 仅在同意后，双方互为好友并出现在彼此好友列表。
- R4. 拒绝后双方不是好友；允许按产品规则再次请求（具体冷却/是否可重发在 design 定一种可测行为）。
- R5. 不能对自己发起请求；对已是好友或已有 pending 的重复请求不产生重复边 / 脏数据（幂等或明确 4xx，design 定一种）。
- R6. 最小 UI：发起请求、待处理（同意/拒绝）、好友列表（足以支撑人工验收；精致通讯录不在范围）。

## Out of Scope

- 从好友开聊 / 移除邮箱建会话（→ open-chat）
- username、全站用户列表、推荐、分组、备注、拉黑、删除好友（删除若实现阶段极低成本可做，**不作为本 PRD 必达**）
- 复杂好友图谱

## Acceptance Criteria

- [ ] AC1. A 用 B 的注册邮箱成功发出请求后，B 的 pending 列表可见该请求。
- [ ] AC2. B 同意后，A 与 B 的好友列表均包含对方；pending 清除。
- [ ] AC3. B 拒绝后，双方好友列表均不包含对方；不残留「已是好友」状态。
- [ ] AC4. 对自己 / 未知策略下的非法请求有明确失败（可测）。
- [ ] AC5. 已是好友或重复 pending 不会插入第二条冲突关系（幂等或 4xx，与 design 一致）。
- [ ] AC6. 对不存在的邮箱：统一可测的失败行为（不要求枚举「是否注册」的信息泄露策略超越「一种稳定错误」）。
- [ ] AC7. 本任务交付后 **不要求** 会话创建 API 已改为好友驱动。

## Key Decisions

| 决策 | 选择 |
|------|------|
| 发现方式 | 仅邮箱（父级 2026-07-29） |
| 关系模型 | **请求 → 同意后互为好友；可拒绝**（父级 2026-07-29） |
